# Implementation Plan

## 前提と注意

- **文書タスクを含める理由**: タスク生成規約は文書作業を対象外としているが、Requirement 7 がリリース手順の記載を要件として持ち、要件は全て網羅する必要がある。そのためタスク 5 として明示的に含める。
- **人間が行う前提作業を含める理由**: npm 側の Trusted Publisher 登録とリポジトリ設定の変更は、実装物が動くかどうかを決める前提であり、隠れた前提を残さないためタスク 6.1 として明示する。実装作業ではなく設定作業である点を各詳細に書く。
- **確認タスクの位置**: ワークフローは GitHub Actions 上でしか実行できないため、初回リリースをリハーサルとして扱い、タスク 6 で実測する。

- [x] 2. バージョン同期の仕組み

- [x] 2.1 バージョン派生と食い違い検査を実装する
  - パッケージのバージョンを唯一の入力とし、2 つの配布物 manifest へ派生させる
  - Gemini 拡張については表示バージョンと起動引数のバージョン指定の 2 か所を同時に更新する。バージョン指定が付いていない引数形にも付与できるようにする
  - 派生の判定と値の組み立ては入力を書き換えない純粋な変換として実装し、ファイルの読み書きと終了コードの決定だけを薄い呼び出し層に置く
  - 検査モードでは書き換えを行わず、違反（対象ファイル・場所・実際の値・期待値）を出力して非ゼロ終了する
  - バージョンが読めない・空の場合は既定値で代替せずその場で失敗させる
  - 両 manifest の変換をすべて済ませてから書き出し、途中失敗で部分的な書き換えを残さない
  - バージョン以外のキー・値・引数の構成は変更しない
  - 完了の見え方: 一致状態では検査が違反ゼロで正常終了し、片方の manifest のバージョンを手で変えると非ゼロ終了して該当ファイルと期待値が出力される
  - _Depends: 1.1_
  - _Boundary: scripts/sync-manifest-versions.ts_
  - _Requirements: 5.1, 5.2, 5.3, 5.4, 6.3_

- [x] 2.2 バージョン同期の単体テストを追加する
  - 表示バージョンと起動引数のバージョン指定が同じ値へ同時に更新されることを検証する
  - 起動引数の他の要素と、manifest の他のキーが変更されないことを検証する
  - プラグイン manifest のバージョンが更新され、他のキーが変更されないことを検証する
  - 検査モードが、一致状態では違反ゼロを返し、不一致状態では対象ファイル・場所・実際の値・期待値を含む違反を返すことを検証する
  - バージョン指定が付いていない起動引数にもバージョンが付与されることを検証する
  - テスト実行対象の設定が `src/` 配下限定になっているため、`scripts/` 配下も対象に含める（この修正が無いとテストが「実行されていないのに成功」して見える）
  - 完了の見え方: 対象ソースと同じ場所に置いたテストが `pnpm test` で実際に実行され（テスト件数が増える）通る
  - _Depends: 2.1_
  - _Boundary: scripts/sync-manifest-versions.test.ts, vitest.config.ts_
  - _Requirements: 5.1, 5.2, 5.3, 5.4, 6.3, 6.4_

- [x] 3. changesets の導入とリリース用スクリプト

- [x] 3.1 (P) changesets を導入する
  - 変更履歴生成の開発依存 2 件を追加する（本体は 2.x 系、変更履歴生成は GitHub 参照付きのもの）
  - 変更履歴生成の対象リポジトリ、基準ブランチ、公開範囲、版上げ時に自動コミットしない設定を入れる

  - 完了の見え方: 変更意図を 1 件記録した状態で状態確認コマンドがその 1 件を認識し、記録が無い状態では対象なしと報告する。lockfile 固定のインストールが成功する

  - _Requirements: 2.1, 2.3, 4.1, 4.2, 4.3_

- [x] 3.2 リリース用スクリプトと公開範囲を整える
  - 派生・検査・版上げ・公開の 4 つのスクリプトを設計で固定した名前で追加する
  - 版上げスクリプトは「版上げ → バージョン派生 → 書き換えた JSON の整形」の順で実行する
  - 公開スクリプトは「整合検査 → ビルド → 公開」の順で実行し、検査が失敗したら公開に進まない
  - 公開物に変更履歴ファイルを含める
  - コマンド提供の定義（`bin`）は変更しない
  - 完了の見え方: 変更意図を 1 件記録した状態で版上げスクリプトを手元で実行すると、パッケージ・変更履歴・2 つの manifest が同じバージョンへ揃った差分になる
  - _Depends: 2.1, 3.1_
  - _Boundary: package.json の scripts と files_
  - _Requirements: 3.2, 3.6, 8.1, 8.4_

- [x] 4. ワークフローの新設

- [x] 4.1 (P) PR チェックワークフローを追加する
  - PR の作成・更新・再オープンで起動し、label・タイトル・変更ファイルによる条件を付けない
  - lint、テスト、バージョン整合の検査の 3 つを実行し、いずれかが失敗したらジョブを失敗させる
  - 依存のインストールは lockfile 固定で行い、実行環境の指定（Node とパッケージマネージャーの版）はリリースワークフローと揃える
  - ジョブ権限は読み取りのみとする
  - 変更意図の記録の有無は検査しない
  - 完了の見え方: PR 上に lint・テスト・整合検査の結果が表示され、意図的に lint 違反を含む PR ではチェックが失敗する
  - _Depends: 2.1_
  - _Boundary: .github/workflows/ci.yml_
  - _Requirements: 1.1, 1.2, 1.3, 5.3_

- [x] 4.2 (P) リリースワークフローを追加する
  - **ファイル名は設計で固定した名前にする**（npm 側の公開許可の登録がワークフローのファイル名に紐づくため、改名は公開の失敗に直結する）
  - 起動条件は既定ブランチへの push と手動実行とし、同時実行を直列化する設定を入れる
  - ジョブ権限は版上げコミットと tag のための書き込み、リリース用 PR のための書き込み、OIDC 公開のための ID トークン発行の 3 つに限る
  - 版上げと公開はリリース用スクリプトの呼び出しに委ね、ワークフロー側にロジックを持たせない
  - tag と GitHub Release の作成は導入する action の既定機能を使い、公開先の dist-tag は既定のまま指定しない
  - 依存のインストールは lockfile 固定で行い、実行環境は OIDC 公開に対応した Node の版を使う
  - 長期有効な公開用トークンをワークフローに置かない
  - 完了の見え方: ワークフロー定義が構文として受理され、権限・起動条件・呼び出すスクリプト名が設計と一致している（実際の公開はタスク 6 で確認する）
  - _Depends: 3.2_
  - _Boundary: .github/workflows/release.yml_
  - _Requirements: 2.2, 3.1, 3.3, 3.4, 3.5, 8.2, 8.3_
