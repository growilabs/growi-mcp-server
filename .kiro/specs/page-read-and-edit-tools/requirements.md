# Requirements Document

## Introduction

ページを読む／編集する MCP ツール群（`getPageOutline` / `getPageSection` / `getPageWholeContents` / `editPage`）の要件を扱う。アウトライン解析の基盤、ページの読み方の分担、応答に載せるフィールドの contract がここに含まれる。

これらのツールの初版は PR #34（merge commit `399e8ba`）で main に入り、そのレビューで洗い出した内容を本 spec がまとめている。Requirement 1（remark 採用）と Requirement 2（ツール再編）はレビューを経た方針転換で、Requirement 3〜8 は内部の整理である。

- **Requirement 1（remark 採用）**: markdown 解析を unified / remark に置き換える。目的は GROWI 本体との出力一致と、CommonMark 準拠部分の保守を外部に委ねること
- **Requirement 2（ツール再編）**: 全文取得を `getPageWholeContents` として明示し、`getPage` はその別名として残したうえで非推奨を告知する

**後方互換の前提**: PR #34 の内容は本 spec の作業時点でまだ公開されていなかった（npm の `@growi/mcp-server` の latest は 1.7.0 で、PR #34 はバージョンを上げていない）。したがって新しい 3 ツールの応答の形にも、既存 3 ツールの応答軽量化（`feat!`）にも、後方互換の制約を課していない。一方 `getPage` は 1.7.0 で公開済みのため、動作を維持したまま非推奨とする経路を採った（Requirement 2）。

## Requirements

### Requirement 1: remark による markdown 解析

**Objective:** MCP クライアント（LLM）として、`getPageOutline` が返す見出しを GROWI の画面に出る見出しと一致させたい。そうすれば、存在しない見出しを指したり、実在する見出しを見落としたりすることがなくなる。

背景: GROWI 本体のページ描画は `remark-parse` + `remark-frontmatter` を使っている（`apps/app/src/services/renderer/renderer.tsx` の `remarkPlugins`）。自前の文字列走査と本体の出力を同じ入力で比較したところ、9 パターン中 5 パターンで結果が異なった（内訳は design.md 参照）。

#### 受け入れ条件（要約）

見出しの検出は `remark-parse` と `remark-frontmatter` による構文木から行い、自前のフェンス走査と frontmatter 判定は削除する。`remark-gfm` は使わない（見出しの検出結果を変えず、解析時間のみ増やすため）。

この置き換えにより、GROWI 本体と同じ次の挙動になる。setext 見出し（`=` または `-` の下線で表す見出し）をアウトラインに含める。HTML ブロックの内側にある見出し形の行は見出しとして報告しない。本文の 1 行目が `---` で閉じ区切りが存在するときはその範囲を frontmatter として扱い、範囲内に見出し形の行があっても報告しない。あわせて `unterminatedFence` フラグを廃止する（未閉フェンス以降の見出しが現れないことは本体と同じ挙動で、本体も警告を出さないため）。

各見出しについては、描画後のテキスト（`text`）と見出し行の生の記法（`raw`）の両方を返し、見出し名から範囲を解決するときは `text` と `raw` のどちらの値でも一致させる。

セクションの終了行・preamble の境界・文字数の算出は構文木からは得られないため、自前の処理として保持する。

### Requirement 2: ページ読み取りツールの再編

**Objective:** MCP クライアント（LLM）として、ページの読み方を名前から選び分けたい。そうすれば「全文が必要なとき」だけ全文を取り、通常はアウトラインと部分読取で済ませられる。

背景: `getPage` という名前からは何が返るか分からず、LLM は既定の入口として選びがちである。PR #34 は説明文での誘導を試みたが、LLM の判断に委ねる弱い手段にとどまっている。一方で `getPage` は 1.7.0 で公開済みであり、意味を入れ替えると「エラーにならず違う内容が返る」という最も見つけにくい壊れ方になる。

#### 受け入れ条件（要約）

全文を返すツールを `getPageWholeContents` という名前で提供し、`getPage` はその別名として維持して同じ応答を返す。**意味を入れ替えてはならない。** 登録は `getPageWholeContents` の実装を共有し、例外処理を含む登録処理を複製しない。

非推奨であることと、代わりに使うべき 3 ツール（`getPageOutline` / `getPageSection` / `getPageWholeContents`）は、`getPage` のツール説明文と応答の両方に置く。応答に載せる案内は、失敗と誤解されない形（エラーでないことが明らかなキー名と 1 文）にする。`getPage` を削除する予定のバージョンは README の英語版・日本語版の両方に明記する。

`getPageInfo` は別の API（`getInfoForPage`）を呼んでおり本 spec の対象外とする。変更しない。

### Requirement 3: アウトライン整形ロジックの単一化

**Objective:** 保守担当として、preamble の境界規則とセクション文字数の数え方を 1 箇所だけに置きたい。そうすれば規則を変えるときに 1 ファイルだけ直せば済む。

背景: `getPageOutline/service.ts` の `charsOfLines` は `parse-outline.ts` の `sliceChars` と 1 文字も違わない複製であり、さらに周辺のコードが preamble の境界規則を再実装している。tool の service 層はページ取得と応答組み立てを担う層であり、アウトラインの意味論を持つべきではない。

#### 受け入れ条件（要約）

`maxDepth` による見出しの絞り込みと、それに伴う preamble の再計算を `parse-outline` モジュールの内部で行う。セクションの文字数を数える関数の実装はシステム全体で 1 つだけとし、`getPageOutline` の service 層はページ本文の行分割を 1 回より多く実行しない。

この整理が振る舞いを変えていないことは、`getPageOutline` の既存テストのうち `unterminatedFence` を検証するもの以外が変更なしで通ることで確認する。

### Requirement 4: editPage の応答フィールドの意味を一意にする

**Objective:** MCP クライアント（LLM）として、`editPage` の応答に含まれるリビジョン ID がどちらの意味なのかをフラグの記憶なしに判別したい。そうすれば次の書き込みで古い ID を楽観ロックに渡して不要な 409 を踏むことがなくなる。

背景: 従来の `EditPageResult.revisionId` は、`dryRun: true` のときは編集前の基準リビジョン、通常実行のときは編集後の新リビジョンを指していた。同じフィールド名に反対の意味が入っており、呼び出し側は `dryRun` を渡したことを覚えていなければ判別できない。

#### 受け入れ条件（要約）

編集の土台にしたリビジョン ID は `dryRun` の有無にかかわらず同じフィールド名で返し、保存で生成されたリビジョン ID は前者とは別のフィールド名で返す（`dryRun` のときは返さない）。保存応答にリビジョンが含まれないときは、古い値を推測で返さない（従来の挙動を維持する）。

`dryRun` の応答に含まれる基準リビジョン ID をそのまま `expectedRevisionId` に渡せることを、ツール説明文に明記する。

### Requirement 5: 到達しないコードの除去

**Objective:** 保守担当として、実行されえない分岐を残さないようにしたい。そうすれば読み手が「この経路も起こりうる」と誤解して不要な考慮をすることがなくなる。

背景: `apply-string-edits.ts` の `findOccurrences` 内の空文字ガードは、唯一の呼び出し元が直前で例外を投げるため到達しない。しかも「呼び出し側が not-found として報告する」というコメントが事実と合っていない。

#### 受け入れ条件（要約）

`applyStringEdits` は公開関数であるため、空の `oldString` に対する防御を 1 つ保持する。ただし到達しない重複した防御は保持しない。

全文取得ツールの例外処理からは、到達しない `GrowiApiError` 分岐を除去する（この経路で `GrowiApiError` を投げるコードは存在しない）。一方 `editPage` / `getPageOutline` / `getPageSection` の登録における同じ分岐は、service が `GrowiApiError` を投げるため到達する。これらは除去しない。

### Requirement 6: 重複した入力検証と応答組み立ての共通化

**Objective:** 保守担当として、同じ判定と同じ組み立てを複数箇所に置かないようにしたい。そうすればフィールドを 1 つ増やすときに直す箇所が 1 箇所で済む。

背景: 「`pageId` か `path` のどちらかが必須」という判定が新規 3 ツールに複製されている。また `editPage` の service は、dryRun・成功時・リトライ成功時の 3 箇所でほぼ同じ形の応答オブジェクトを手で組み立てており、行数と文字数の算出が 3 回書かれている。

#### 受け入れ条件（要約）

「`pageId` か `path` のどちらかが必須」の判定を共通の関数として 1 箇所に持ち、各登録処理からはそれを呼び出す。この判定は zod スキーマの `.refine()` ではなく登録層に置き続ける（fastmcp が `parameters` に素の `z.object` を要求するため）。

`editPage` の応答オブジェクトの組み立ては 1 つの関数に集約する。

### Requirement 7: テストによる契約の固定

**Objective:** レビュー担当として、振る舞いが変わった箇所と変わっていない箇所を、テストの差分から区別できるようにしたい。そうすれば意図した変更と事故を見分けられる。

背景: このリポジトリには CI が 1 つも設定されていないため、テストの通過状況が実質的に唯一の検出手段である。Requirement 1 は多くのテストの期待値を変えるので、「どのテストがなぜ変わるか」を事前に確定させておく必要があった。

#### 受け入れ条件（要約）

テストで固定する契約は次の 3 点。

- 前半が一致し後半が一致しない編集列を `editPage` に渡したとき、保存を 1 度も試みずに例外を投げる
- 見出しテキストが空になる行（`#` のみの行）に対するアウトラインの振る舞いを決めて固定する
- `getPage` が別名として同じ応答を返し、かつ非推奨の案内を含む

加えて実装時の運用として、Requirement 1 によって変わる既存テストの一覧（変更・削除・新規）を着手前に design.md へ確定させ、その一覧に無いテストが変更を要したら想定外の振る舞い変更として作業を止める、という手順を課した。実装完了に伴いこの一覧は design.md から削除しており、現在はテストコード自体がその記録である。

### Requirement 8: 権限情報をメタデータとして返す

**Objective:** MCP クライアント（LLM）として、ユーザー指定公開のページで誰に閲覧権限があるかを、本文を取得せずに確認したい。そうすればページの公開範囲を誤って説明することがなくなる。

背景: PR #34 の応答軽量化により `grantedUsers` が `grantedUsersCount` に置き換わり、権限保持者を確認する手段が失われた。`seenUsers` と `liker` は閲覧されるたびに際限なく増えるので件数化が妥当だが、`grantedUsers` は作成者が意図して設定する権限情報であり、性質が異なる。実際の応答は ID 文字列の配列（SDK v3 の宣言は `grantedUsers?: string[]`）で、件数も通常は少数にとどまる。加えて `grantedGroups` は PR #34 で件数化されておらず、グループ指定の権限だけが読めてユーザー指定の権限が読めない状態になっていた。

#### 受け入れ条件（要約）

ページ応答には `grantedUsers` の実体を含め、件数への置き換えをしない。`grantedUsersCount` も併せて返す。`grantedUsers` の要素がオブジェクトとして返された場合は `{ _id, username }` に縮小し、ID 文字列の場合はそのまま通す。`seenUsers` と `liker` は閲覧のたびに際限なく増えるため、件数のみを返し続ける。

本文を取得せずにページのメタデータを読めるようにするため、`getPageOutline` の応答にもページのメタデータ（`parent`・`grant`・`grantedUsers`・タグ等）を含める。本文を除いた同じ整形処理を通すものとする。`getPageOutline` はすでにページ文書全体を取得しているため、この追加によって API 呼び出しが増えてはならない。
