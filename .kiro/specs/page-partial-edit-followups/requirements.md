# Requirements Document

## Introduction

PR #34（merge commit `399e8ba`）で部分読取・部分編集の 3 ツール（`getPageOutline` / `getPageSection` / `editPage`）と、既存 3 ツールの応答軽量化が main に入った。本 spec はそのレビューで洗い出した追随作業を扱う。

**前提: PR #34 はまだ公開されていない。** npm の `@growi/mcp-server` の latest は 1.7.0 で、PR #34 はバージョンを上げていない。したがって新しい 3 ツールには利用者がおらず、その応答の形を変えても誰も壊れない。既存 3 ツールの応答軽量化（`feat!`）も同様に未公開である。

この事実から、本 spec は **1.8.0 の公開前に完了させること** を目標に据える。公開後に同じ整理をすると、新ツールにも利用者がついて費用が確実に上がる。

本 spec には、レビューを経て方針転換した 2 件（Requirement 1・2）と、当初からの追随作業（Requirement 3〜8）が含まれる。

- **Requirement 1（remark 採用）**: markdown 解析を unified / remark に置き換える。目的は GROWI 本体との出力一致と、CommonMark 準拠部分の保守を外部に委ねること
- **Requirement 2（ツール再編）**: 全文取得を `getPageWholeContents` として明示し、`getPage` はその別名として残したうえで非推奨を告知する

後方互換について: 1.7.0 で公開済みの `getPage` は動作を維持する（Requirement 2）。それ以外の対象コードはすべて未公開なので、後方互換の制約を課さない。

## Requirements

### Requirement 1: remark による markdown 解析

**Objective:** MCP クライアント（LLM）として、`getPageOutline` が返す見出しを GROWI の画面に出る見出しと一致させたい。そうすれば、存在しない見出しを指したり、実在する見出しを見落としたりすることがなくなる。

背景: GROWI 本体のページ描画は `remark-parse` + `remark-frontmatter` を使っている（`apps/app/src/services/renderer/renderer.tsx` の `remarkPlugins`）。自前の文字列走査と本体の出力を同じ入力で比較したところ、9 パターン中 5 パターンで結果が異なった（内訳は design.md 参照）。

#### Acceptance Criteria

1. システムは見出しの検出を `remark-parse` と `remark-frontmatter` による構文木から行わなければならない。自前のフェンス走査と frontmatter 判定は削除しなければならない。
2. `remark-gfm` を使ってはならない。見出しの検出結果に影響せず、解析時間のみ増やすためである。
3. 各見出しについて、システムは描画後のテキスト（`text`）と見出し行の生の記法（`raw`）の両方を返さなければならない。
4. 見出し名から範囲を解決するとき、システムは `text` と `raw` のどちらの値でも一致させなければならない。
5. setext 見出し（`=` または `-` の下線で表す見出し）を、システムはアウトラインに含めなければならない。
6. HTML ブロックの内側にある見出し形の行を、システムは見出しとして報告してはならない。
7. 本文の 1 行目が `---` で閉じ区切りが存在するとき、システムはその範囲を frontmatter として扱い、範囲内のいかなる行も見出しとして報告してはならない。範囲内に見出し形の行が含まれる場合も同様とする。
8. `unterminatedFence` フラグを、システムは廃止しなければならない。未閉フェンス以降の見出しがアウトラインに現れないことは GROWI 本体と同じ挙動であり、本体も警告を出さないためである。
9. セクションの終了行・preamble の境界・文字数の算出は、構文木からは得られないため、システムは自前の処理として保持しなければならない。

### Requirement 2: ページ読み取りツールの再編

**Objective:** MCP クライアント（LLM）として、ページの読み方を名前から選び分けたい。そうすれば「全文が必要なとき」だけ全文を取り、通常はアウトラインと部分読取で済ませられる。

背景: `getPage` という名前からは何が返るか分からず、LLM は既定の入口として選びがちである。PR #34 は説明文での誘導を試みたが、LLM の判断に委ねる弱い手段にとどまっている。一方で `getPage` は 1.7.0 で公開済みであり、意味を入れ替えると「エラーにならず違う内容が返る」という最も見つけにくい壊れ方になる。

#### Acceptance Criteria

1. システムは全文を返すツールを `getPageWholeContents` という名前で提供しなければならない。
2. システムは `getPage` を `getPageWholeContents` の別名として維持し、同じ応答を返さなければならない。意味を入れ替えてはならない。
3. `getPage` のツール説明文に、非推奨であることと `getPageOutline` / `getPageSection` / `getPageWholeContents` のいずれかを使うべきことを、システムは明記しなければならない。
4. `getPage` の応答に、非推奨であることを伝える短い案内を、システムは含めなければならない。この案内は失敗と誤解されない形（エラーでないことが明らかなキー名と 1 文）でなければならない。
5. `getPage` の登録は `getPageWholeContents` の実装を共有しなければならない。例外処理を含む登録処理を複製してはならない。
6. `getPage` を削除する予定のバージョンを、システムは README（英語版・日本語版の両方）に明記しなければならない。
7. `getPageInfo` は別の API（`getInfoForPage`）を呼んでおり本 spec の対象外とする。システムはこれを変更してはならない。

### Requirement 3: アウトライン整形ロジックの単一化

**Objective:** 保守担当として、preamble の境界規則とセクション文字数の数え方を 1 箇所だけに置きたい。そうすれば規則を変えるときに 1 ファイルだけ直せば済む。

背景: `getPageOutline/service.ts` の `charsOfLines` は `parse-outline.ts` の `sliceChars` と 1 文字も違わない複製であり、さらに周辺のコードが preamble の境界規則を再実装している。tool の service 層はページ取得と応答組み立てを担う層であり、アウトラインの意味論を持つべきではない。

#### Acceptance Criteria

1. `maxDepth` による見出しの絞り込みと、それに伴う preamble の再計算を、システムは `parse-outline` モジュールの内部で行わなければならない。
2. セクションの文字数を数える関数の実装は、システム全体で 1 つだけ存在しなければならない。
3. `getPageOutline` の service 層は、ページ本文の行分割を 1 回より多く実行してはならない。
4. `getPageOutline` の既存テストのうち、`unterminatedFence` を検証するもの以外は、変更なしで通らなければならない。

### Requirement 4: editPage の応答フィールドの意味を一意にする

**Objective:** MCP クライアント（LLM）として、`editPage` の応答に含まれるリビジョン ID がどちらの意味なのかをフラグの記憶なしに判別したい。そうすれば次の書き込みで古い ID を楽観ロックに渡して不要な 409 を踏むことがなくなる。

背景: 現在の `EditPageResult.revisionId` は、`dryRun: true` のときは編集前の基準リビジョン、通常実行のときは編集後の新リビジョンを指す。同じフィールド名に反対の意味が入っており、呼び出し側は `dryRun` を渡したことを覚えていなければ判別できない。

#### Acceptance Criteria

1. 編集の土台にしたリビジョン ID を、システムは `dryRun` の有無にかかわらず同じフィールド名で返さなければならない。
2. 保存で生成されたリビジョン ID を、システムは前者とは別のフィールド名で返さなければならない。`dryRun` のときは返してはならない。
3. 保存応答にリビジョンが含まれないとき、システムは古い値を推測で返してはならない（現在の挙動を維持する）。
4. `dryRun` の応答に含まれる基準リビジョン ID をそのまま `expectedRevisionId` に渡せることを、システムはツール説明文に明記しなければならない。

### Requirement 5: 到達しないコードの除去

**Objective:** 保守担当として、実行されえない分岐を残さないようにしたい。そうすれば読み手が「この経路も起こりうる」と誤解して不要な考慮をすることがなくなる。

背景: `apply-string-edits.ts` の `findOccurrences` 内の空文字ガードは、唯一の呼び出し元が直前で例外を投げるため到達しない。しかも「呼び出し側が not-found として報告する」というコメントが事実と合っていない。

#### Acceptance Criteria

1. `applyStringEdits` は公開関数であるため、空の `oldString` に対する防御を 1 つ保持しなければならない。ただし到達しない重複した防御は保持してはならない。
2. 全文取得ツールの例外処理から、到達しない `GrowiApiError` 分岐をシステムは除去しなければならない（この経路で `GrowiApiError` を投げるコードは存在しない）。
3. `editPage` / `getPageOutline` / `getPageSection` の登録における同分岐は、service が `GrowiApiError` を投げるため到達する。これらは除去してはならない。

### Requirement 6: 重複した入力検証と応答組み立ての共通化

**Objective:** 保守担当として、同じ判定と同じ組み立てを複数箇所に置かないようにしたい。そうすればフィールドを 1 つ増やすときに直す箇所が 1 箇所で済む。

背景: 「`pageId` か `path` のどちらかが必須」という判定が新規 3 ツールに複製されている。また `editPage` の service は、dryRun・成功時・リトライ成功時の 3 箇所でほぼ同じ形の応答オブジェクトを手で組み立てており、行数と文字数の算出が 3 回書かれている。

#### Acceptance Criteria

1. 「`pageId` か `path` のどちらかが必須」の判定を、システムは共通の関数として 1 箇所に持ち、各登録処理からはそれを呼び出さなければならない。
2. `editPage` の応答オブジェクトの組み立てを、システムは 1 つの関数に集約しなければならない。
3. fastmcp が `parameters` に素の `z.object` を要求するため、この判定は zod スキーマの `.refine()` ではなく登録層に置き続けなければならない。

### Requirement 7: テストによる契約の固定

**Objective:** レビュー担当として、振る舞いが変わった箇所と変わっていない箇所を、テストの差分から区別できるようにしたい。そうすれば意図した変更と事故を見分けられる。

背景: このリポジトリには CI が 1 つも設定されていないため、テストの通過状況が実質的に唯一の検出手段である。Requirement 1 は多くのテストの期待値を変えるので、「どのテストがなぜ変わるか」を事前に確定させておく必要がある。

#### Acceptance Criteria

1. Requirement 1 によって変わる既存テストの一覧（変更・削除・新規）を、システムの担当者は着手前に確定させなければならない（design.md の Testing Strategy に記載する）。
2. その一覧に無いテストが変更を要したとき、担当者は想定外の振る舞い変更として作業を止めなければならない。
3. 前半が一致し後半が一致しない編集列を `editPage` に渡したとき、システムは保存を 1 度も試みずに例外を投げなければならない。この振る舞いはテストで検証されなければならない。
4. 見出しテキストが空になる行（`#` のみの行）に対するアウトラインの振る舞いを、システムは決定し、テストで固定しなければならない。
5. `getPage` が別名として同じ応答を返し、かつ非推奨の案内を含むことを、システムはテストで検証しなければならない。

### Requirement 8: 応答軽量化で失われた権限情報の扱いの決定

**Objective:** MCP クライアント（LLM）として、ユーザー指定公開のページで誰に閲覧権限があるかを確認できる経路を持ちたい。そうすればページの公開範囲を誤って説明することがなくなる。

背景: PR #34 の応答軽量化により `grantedUsers` が `grantedUsersCount` に置き換わった。`seenUsers` と `liker` を件数化するのは妥当だが、`grantedUsers` は権限そのものの情報である。この変更も未公開なので、今なら自由に決め直せる。

#### Acceptance Criteria

1. `grant` がユーザー指定公開のページについて、権限保持者を確認できる代替経路が存在するかを、システムの担当者は調査しなければならない。
2. 代替経路が存在しない場合、`grantedUsers` を件数化したままにするか復帰させるかを、担当者は判断し本 spec に記録しなければならない。
3. `getPageOutline` の応答にページのメタデータ（`parent`・`grant`・タグ等）を含めるかどうかを、担当者は本要件と併せて判断しなければならない。
